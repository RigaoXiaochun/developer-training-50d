# Q17 合并两份都能跑的改动

第 40–41 天，留 2 天。预计用时 4 小时。

从同一版本开两个训练分支，一个改校验，一个改布局。在临时整合分支合并，解决一处文本冲突，再找一处 Git 没报错但实际改变行为的问题。

先在 `exercises/Q17.ts` 独立完成 `threeWayMerge`。看[Q17 核心函数](../核心编码契约.md#q17-threewaymerge)，补三个自己设计的反例，先做一次核心提交，再请工具协助后面的工程改动。

从 [本题引导](../引导/02_GitHub交付.md) 开始。接口以 [接口与数据](../契约/接口与数据.md) 为准。分支用 `feat/q17-integration-review`。

## 改动范围

- `frontend/vue/`
- `tests/learner/`
- `learning/Q17/`

## 具体要求

- 按固定协作卡，从同一基线建立自己仓库的A／B演练分支，分别实现校验与布局变更，各有独立提交。
- 在临时整合分支合并，解决一次文本冲突，再查一处没有Git冲突但覆盖行为的语义冲突。
- 让Agent给出冲突说明与候选合并，不直接接受ours／theirs；本人核对双方验收与回归。
- 记录共同基线、两分支SHA、整合SHA及验证；通过后按个人训练流程合回main，不强推历史。

## 交什么

交共同基线、两支 SHA、整合 SHA 和验证记录。说明合并时保留了哪条校验、哪项交互。

在 `learning/Q17/` 留 [交付记录](../模板/交付模板.md)，把实际失败和没有做过的检查写清楚。

- 两项原始需求都保留，合并通过不是仅消除冲突标记。
- 完整SHA和合并顺序可复现；旧用户数据不因代码恢复清空。
- 能够不用AI解释三方合并、revert与reset的风险差别。
