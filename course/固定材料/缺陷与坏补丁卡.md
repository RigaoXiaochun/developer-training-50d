# 固定缺陷与审查卡

这些片段用于阅读、隔离复现和审查，不直接合入主分支。要说明可触发条件和最小修复，不只说代码不好。

## A 旧响应覆盖

```js
async function search(q) {
  rows.value = await api.list({ q });
}
```

条件：先搜A再搜B，A更晚完成；同时考虑角色切换。找出需要区分的状态，提出实验和修复，不能靠延迟固定200ms碰运气。

## B 所有方法都重试

```js
async function request(url, init) {
  try { return await fetch(url, init); }
  catch { return await fetch(url, init); }
}
```

条件：创建实际已落库但响应断开。说明幂等key、请求意图和重放边界；不能仅把retry次数改小。

## C 吞掉错误

```js
try { await save(draft); }
catch { return []; }
finally { notice.value = '保存しました'; }
```

指出返回类型、成功语义和用户输入受影响的路径。修复后分别验证成功、失败和处理中结束。

## D 权限条件被放大

```js
return actor.role === 'staff' || ticket.assigneeId === actor.id;
```

用至少两种越权反例和归档反例说明；不仅把OR换成AND，还需完整角色和对象模型。

## E SQL“优化”

```js
const sql = "SELECT * FROM tickets WHERE title LIKE '%" + q + "%'";
```

审查输入拼接、角色条件、归档、字段投影、分页和搜索索引限制。改成参数化只解决其中一类问题。

## F 交付越界

原需求只改筛选布局，Agent同时更新package-lock、替换共享Button、移除409断言，并在报告写“全部通过”。按风险排序指出需证据和应拒绝的改动，不能因为最终图更好看就接受。
