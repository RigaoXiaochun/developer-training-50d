# 业务原话练习

动手前先读对应场景的业务原话，在 `learning/Qxx/上下文.md` 写出自己的理解。再查固定需求、接口和任务书，标出哪些已有依据，哪些还缺确认。遇到材料没有回答的问题，写明它会影响哪项行为，并按任务书明确的部分继续。

## Q01 · 一句话里有哪些待确认事项

> 我们需要个工单台，大家报上来的问题有人接，负责人一眼能知道进度。手机上也得能用。

先找出「大家」「有人接」「负责人」「进度」各指什么。写五个会改变实现的问题，例如某种角色在某个状态下能看见或操作什么。查 [工单台需求说明](业务原话与FAQ.md) 和 [接口与数据规范](../契约/接口与数据.md)，给每个问题写明出处、结论或待确认原因。此题的工程改动按 Q01 的任务范围执行。

## Q03–Q04 · 把界面反馈变成原型验证

> 手机上看个工单太费劲了。标题一长，想点进去还得来回找。列表和表单也不像一个系统。

从实际操作判断问题发生在哪里，再选一个小场景做原型。下面示范把「想点进去得来回找」写成可验证的要求。

1. **操作目标**　工作人员在窄屏扫列表，能找到指定工单并进入详情。
2. **验收条件**　390 px 下，长标题出现时，状态和详情入口仍可见，页面没有横向滚动。进入详情能看到完整标题。列表入口用键盘也能聚焦。其他视口和控件规格按 [UI 与交互标准](../规范/UI与交互.md) 检查。
3. **原型任务**　请先做一条工单列表行，复用现有设计变量与控件，用短标题和长标题两条样例。列出准备调整的控件和验证方法。暂不接 API。
4. **反馈与复测**　先在 390 px 打开原型，再用实际观察给下一轮反馈。例如「状态标签占了两行，详情按钮掉到下一行」要附触发条件。修订后用同一数据复测，再用键盘检查入口。

正式练习用 [界面评审材料](原型反馈与迭代.md) 做两轮调整。其他反馈按实际操作结果判断。

## Q08–Q09 · 把「重试」分成两个业务动作

> 有时点提交没看到成功，再点一次就多出一张单。编辑被别人抢先改了，我刚填的内容也找不回来了。

分别记下「创建结果未知」与「保存版本冲突」时用户看见什么、系统保存了什么、再次操作应发生什么。查接口约定后，选择一个能以请求和数据复现的场景交给工具辅助实现。验收时重放该场景，核对响应、工单记录和事件，可附页面截图。

## Q16 · 需求变更

> 先让我只看高优先级的单，但我也得知道别的优先级还有多少。刷新以后，这个筛选别丢。

先写出决定统计结果的条件。用一个组合场景说明「当前选了高优先级」和「某些工单对这个角色不可见」分别影响哪些结果。然后对照 [CR-01](业务原话与FAQ.md#需求变更-cr-01q16)，整理保留项、变更项及回归路径，再决定第一处代码改动。

## Q20 · 结业交付

从 [设备借还系统任务书](结业项目任务书.md) 的业务原话开始。先提出会改变实现的问题，再根据带教回复写出改动范围和验收条件。用 GitHub 跟进需求及验证，交付可独立启动的系统。现场用自己的实现解释取舍、故障情形和验证结果。
