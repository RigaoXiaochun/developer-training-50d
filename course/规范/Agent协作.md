# Vibe Coding 与开发验收

## 独立编码

每项先独立完成 `exercises/` 中的核心函数和自拟反例。完成单独提交后，工程修改可以使用辅助工具。若工具已给出当前独立题的实现，本次作为练习，由审核人另选样例完成独立核验。

## 从业务原话到提交

1. **先理解需求。** 写下哪个角色在什么场景遇到了问题、期望看到什么结果。对照任务书和现有代码，把事实、待确认项和本轮范围写进 `上下文.md`。权限、状态变化和统计口径有歧义时，列出需要课程负责人确认的问题。
2. **先验证一小段。** 把角色、输入、初始状态、预期结果和允许改动的范围交给工具。先让它列出方案与假设，选一条关键路径做出可运行的原型。界面原型用已有设计变量和样例数据。接口类任务可以从一条本地请求或测试开始。
3. **用实际反馈修订。** 学员亲自操作或运行检查，把「不好用」「没成功」写成明确的触发条件、实际结果和期望行为。再让工具处理对应改动。审阅差异时，核对权限、接口、数据口径和共享控件行为是否符合约定。
4. **按同一场景验收。** 用同一数据和操作重新验证，补异常和回归检查。把一处关键修改、取舍与验证结果记入 `审查.md`，在 PR 中概述需求、改动及复现步骤。截图对应操作过程，测试记录对应提交版本。

从 [业务原话练习](../固定材料/业务原话练习.md) 选对应的场景开始。Q03、Q04 用 [原型反馈](../固定材料/原型反馈与迭代.md) 完成界面迭代。Q16 练习处理需求变更，Q20 练习从接到业务原话到完成交付。辅助工具可以帮忙做原型、提方案和分析差异，学员负责确认需求、决定改动和验收。交付记录保留其中与实际决定有关的内容。
